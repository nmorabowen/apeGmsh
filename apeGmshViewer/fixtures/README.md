# Fixtures

## `shoebuckle.h5`

A 2-D frame of 123 `dispBeamColumn` elements (two columns and a circular arch)
with the full beam definition chain: `geomTransf Linear` → `beamIntegration
Legendre` (2 points) → `section Fiber` (3 patches) → `uniaxialMaterial
ASDSteel1D`. Neutral schema 2.35.0, OpenSees schema 2.22.0, 0.19 MB. The
writer also stamps `/meta/session_id` and its own `/provenance` zone (1.1.0,
#1378) whose `@base_dir` is this directory on the generating machine.

It was generated by the apeGmsh example `examples/shoebuckle_arch.py`, run from
the repository root on commit `38b482bb` with the opensees venv interpreter. The
command builds the mesh and the OpenSees declarations and writes `model.h5`; it
runs no analysis:

```powershell
$env:PYTHONPATH = "src"
& C:\Users\nmora\venv\opensees_venv\Scripts\python.exe -c "import sys; sys.path.insert(0, 'examples'); import shoebuckle_arch as s; fem = s.build_fem(); ops = s.declare_model(fem); ops.h5('apeGmshViewer/fixtures/shoebuckle.h5')"
```

The generator is not part of this app and is not copied here (ADR 0112 D4).
If the example and the writer are unchanged, a re-run changes
`/meta/created_iso`, the lineage hashes, `/meta/session_id` (new every run),
and the `/provenance` paths: `@base_dir` and the absolute path of
`examples/shoebuckle_arch.py` are the generating checkout's. The `-c` command
is the script, so `/provenance/files` also holds the pseudo-file `<string>`
with an empty `sha256` (h5-schema.md, "Files").

The tests in `test/fixture.test.ts` check this file against closed forms of the
example's parameters (span, column height, rise, element size, section
dimensions, material constants), not against values copied from the app.

## `bridge_provenance.h5`

A `model.h5` written by `main`'s own writer (commit `281154bf`, after #1378):
`/provenance` 1.1.0 with the `records/origin` column, neutral 2.35.0 and
OpenSees 2.22.0. A tetrahedral unit box with one material, one element
declaration and one stage, `gravity`, whose `s.support(...)` makes the bridge
synthesise two objects: `opensees/timeSeries/support:gravity/hold` and
`opensees/pattern/support:gravity`, each with `origin = "synthesised"` and
the site of the `s.support(...)` line. Every other record is `user`.

The script below is the whole generator, run as `bridge_model.py` from an
empty directory with `PYTHONPATH` set to the repository's `src` and the opensees
venv interpreter; it writes `model.h5` there, which is copied here. The
recorded `@base_dir` is that directory, and the file's `sha256` is this
script's digest with LF line ends. Like `shoebuckle.h5`, the generator imports
apeGmsh, so it is kept here as text and never as a `.py` file of the app
(ADR 0112 D4).

```python
from apeGmsh import apeGmsh
from apeGmsh.opensees import apeSees

with apeGmsh(model_name="bridge_provenance", verbose=False) as g:
    g.model.geometry.add_box(0, 0, 0, 1, 1, 1, label="block")
    g.physical.add_volume("block", name="Block")
    g.mesh.sizing.set_global_size(1.0)
    g.mesh.generation.generate(dim=3)
    fem = g.mesh.queries.get_fem_data(dim=3)

ops = apeSees(fem)
ops.model(ndm=3, ndf=3)
concrete = ops.nDMaterial.ElasticIsotropic(E=30e9, nu=0.2, rho=0.0, name="concrete")
ops.element.FourNodeTetrahedron(pg="Block", material=concrete)
with ops.stage(name="gravity") as s:
    s.support(pg="Block", dofs=(1, 1, 1))
    s.analysis(
        test=ops.test.NormDispIncr(tol=1e-4, max_iter=50),
        algorithm=ops.algorithm.Newton(),
        integrator=ops.integrator.LoadControl(dlam=0.1),
        constraints=ops.constraints.Plain(),
        numberer=ops.numberer.RCM(),
        system=ops.system.UmfPack(),
        analysis=ops.analysis.Static(),
    )
    s.run(n_increments=1)
ops.h5("model.h5")
```

`test/zones/provenance.test.ts` checks the fixture against this block: the
digest, and the synthesised records' line, which is the `s.support(` line.

## `results_small.h5`

A native `results.h5` (results zone 1.1.0, `source_type = "domain_capture"`,
`/model` embedded, one partition). It is written by apeGmsh's own
`NativeWriter`, with synthetic values and no solve. The mesh is 2 x 2
triangles extruded in 1 layer: 18 nodes and 8 `prism6`. It has 5 steps,
`displacement_x/y/z`, and one gauss group of 6 points holding `stress_xx`
and `stress_yy`. The generator imports apeGmsh, so it lives outside this
app, at `scripts/make_viewer_results_fixtures.py` in the repository. Run it
from the repository root with `PYTHONPATH=src` and the opensees venv
interpreter:

```powershell
$env:PYTHONPATH = "src"
& C:\Users\nmora\venv\opensees_venv\Scripts\python.exe scripts/make_viewer_results_fixtures.py
```

The same script with `--measure <dir>` writes the large files that
`MEASUREMENTS.md` ("Results sizes (V4)") measures; they are not committed.
`test/results/results.test.ts` checks the reader against the closed forms in
the script's docstring, not against values copied from the app. A re-run
changes `@created_at` and the lineage hashes.

The file has no `element_index_space` stamp, so its element rows read as
`unverified` (h5-schema.md §`element_index_space`; stamp-only, #1768).

## `results_stamped.h5`

The same mesh, steps and closed forms as `results_small.h5`, written at the
writer's current results version (1.2.0) with
`NativeWriter.stamp_element_index_space("fem")`, so its element rows are
verified FEM ids. `test/results/results.test.ts` uses it for the verified
mapping and for the stamp cases (removed, unknown value, non-string). Write
it with the same command plus `--stamped`.

`--stamped` also writes `stamp_variants/`: copies of `results_stamped.h5`
whose stamp h5py re-encodes (variable-length UTF-8 and ASCII str, ASCII
bytes, fixed-length ASCII and UTF-8, NUL-padded or exact, a one-element
array), and `stamp_variants.oracle.json`, Python's
`NativeReader.element_index_verified` on each. The test checks the app's
verdict against it: only a scalar variable-length UTF-8 string `"fem"`
verifies (#1810 review, #1811).

## `staged_activation.h5`, `staged_activation.results.h5` and `staged_activation.oracle.json`

The V4b staged pair (#1728). `staged_activation.h5` is a composed `model.h5`
(neutral 2.35.0, OpenSees 2.27.0, `/sequence` 1.0.0) of three touching
tet-meshed boxes, 314 nodes and 743 `FourNodeTetrahedron` elements: `Col`
(348) and `Prop` (220) are global, and three stages run `base`, then
`erect` (`s.activate(pgs=["Top"])`, the 175 `Top` elements), then `unprop`
(`s.remove_element(pg="Prop")`). `staged_activation.results.h5` is written by
`NativeWriter` with `model_h5_src=` the model, so its `/meta/lineage`
carries the model's `model_hash`; it has one `static` stage per program
stage, by name (3, 2 and 4 steps, `time[k] = (k + 1) / T`), and a `mode`
stage `mode_1` that no program stage names. The values are synthetic
(`displacement_x[k, j] = id_j + 0.001 k`); no solve runs.
`staged_activation.femonly.results.h5` holds the same three stages written
without `model_h5_src`: no `/opensees`, so no `model_hash`; it pairs with the
model by `fem_hash` only, and its stage activation must stay `unbound`.
`staged_activation.oracle.json` is Python's
`viewers/data/_stage_activation.py::build_from_model` on the model, run by
the same script outside the app: the FEM ids each program stage hides.
`test/results/activation.test.ts` compares the app's activation with it.

```powershell
$env:PYTHONPATH = "src"
& C:\Users\nmb\venv\opensees_venv\Scripts\python.exe scripts/make_viewer_results_fixtures.py --staged
```

The session writes its own `model.h5` and geometry sibling into a temporary
directory, not here; `/provenance` records the generating checkout's paths.
A re-run changes the lineage hashes, `/meta/session_id` and the timestamps;
re-run all three files together, since the oracle is read from this model.

## `contour_staged.*` and `contour_nodata.*`

The V4c1 contour pairs (#1756). `contour_staged.h5` is the staged model
above, built again under its own name (314 nodes, 743 tets; `Col`, `Prop`,
`Top`; stages `base`, `erect`, `unprop`). `contour_staged.results.h5`, written
by `NativeWriter` with `model_h5_src=` the model, holds the three program
stages (3, 2 and 4 steps, `time[k] = (k + 1) / T`) with `displacement_x`,
`displacement_y` and `displacement_z` of every node, closed forms of the
node coordinates, for stage index `i` and step `k`:

    s = 0.01 (i + 1) (k + 1) / T
    displacement_x = s z,   displacement_y = 0.5 s x,   displacement_z = -0.2 s (x + z)

`contour_nodata.h5` is the same model file under another stem (so the same
hashes), and `contour_nodata.results.h5` records only the nodes with
`z <= 3`: the 48 nodes of the `Top` box above its base are absent from
`_ids`, the "no data" case. `test/contour/oracle.test.ts` checks the app's
per-vertex values, colours and history range against the closed form,
restated in `test/contour/harness.ts`, not copied from the app. The values
are synthetic; no solve runs.
